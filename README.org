** Data Entry and Bot Setup

*** Configuration Setup: Bot Token and Data Reference
     Each bot contains a ~resources~ folder. You need to put in there
     the ~.token~ file containing the telegram key specific to each
     bot.

     Each bot also uses a ~SQLite~ Database! So you need to provide
     the path to the database into the ~application.conf~ or just set
     up the specific environment variables. No need to put the files
     in ~resources~ folder anymore (even if it's still potentially
     possible a little code change) since those will be fetched from
     the web via URLs or by Telegram Ids.

*** Data Entry

     To add data to the bots you need to:
     - Add the file name, Telegram ~file_id~ and/or downloadable link (usually Dropbox), to the json at the root of each bot folder. To get the ~file_id_~ you can take advantage of [[https://t.me/jsoonbot][@jsonbot]] by just sending the file and copy the id from the reply.
     - Modify the scala code to add the type that creates the mappings between the triggers and the files. See planty of examples of any kind throughout the code, especially under RichardPHJBensonBot's data package.

** Database Setup

     There's a module called ~botDB~, if opportunely configured,
     when launched, it applies the migrations and populates a bot
     database.

     Just set up:
     - The ~application.conf~ correctly with the:
       - DB path, see the DB in the root of the project
       - Location of the ~jsons~. There should be a ~json~ file at the root of each bot module
       - shows youtube sources by bot containing the:
         - list of playlist id or channel handle
         - bot name
         - relative output path, from BotDB folder, of the shows where to save the results.
     - The Youtube Api file named ~youTubeApiKey.token~ with the API key from google console placed in ~/modules/botDB/src/main/resources/~

** Compile and Test

  Several command alias are defined in the project to group together useful ~sbt~ commands:
  - ~dbSetup~ :: Run the botDB main that set up the DB anew. Running the migrations and updating the media tables based on the JSON in the bots folders.
  - ~fix~ :: Mutating: ~scalafmt~/~scalafix~ plus regeneration of triggers, calendars and instructions. Run locally after bot data changes; never in CI.
  - ~check~ :: Read-only formatting and explicit-dependency checks using ~sbt~ plugins such as ~scalafmt~.
  - ~verify~ :: Full read-only verification: ~check~, instruction check, ~dbSetup~, coverage, unit and integration tests, assembly. This is the CI path.
  - ~validate~ :: Deprecated alias of ~verify~. It used to include ~fix~; it no longer writes files.
  - ~integrationLiveNetworkTests~ :: Opt-in live Dropbox/Mega integration tests (tagged ~LiveNetwork~, excluded from ~verify~). Also available as the "Live-network integration tests" manual GitHub workflow.
  - ~checkAllLinksTest~ :: Run a parallel test and checks all the
    media links in the DB and can be called manually by ~sbt
    integration/runIntegrationScalaTests~. Run it once in a while
    (especially after a series of new additions or changes in links)
    to be sure everything is still reachable and up. These tests
    excluded from the CI because they are quite slow.

** Healthcheck

  When running the webhook main (~MainWebhook~), the application
  periodically pings an external healthcheck endpoint so you can
  monitor that the service is up (e.g. [[https://healthchecks.io][healthchecks.io]]).

  - *Where*: The healthcheck runs in the main module, in the webhook and
    in the polling mode; one background fiber pings the configured URL
    on a cron schedule. It also pings ~<url>/start~ on boot and
    ~<url>/fail~ (with the error as the body) when the application
    crashes; a failed ping is only logged, and the fiber starts again
    after an error.
  - *Config*: In ~modules/main/src/main/resources/application.conf~
    under ~main.healthcheck-ping~:
    - ~endpoint~ :: URL to POST (e.g. ~https://hc-ping.com/<your-check-uuid>~).
    - ~cron~ :: Cron4s expression for how often to ping (e.g. ~* */10 * ? * *~ for every 10 minutes).
  - *Overrides*: You can override with env vars if your config
    supports it; otherwise edit ~application.conf~ before assembly.
  - *Note*: Only one healthcheck fiber is started per process. If you
    run multiple replicas, each will ping the same endpoint on each
    tick.

** LLM Replies

The bots can answer with a free-tier LLM when they are addressed. The reactive replies stay first: the LLM is only asked
when nothing else matched. The behaviour is specified in ~specs/llm.allium~, the dispatch is in
[[file:docs/bot-logic-overview.md][bot-logic-overview]] (see "LLM replies") and the logs and dashboard in
[[file:docs/monitoring.md][monitoring]].

*** Enabling it

1. Set the repository secrets ~GEMINI_API_KEY~ and ~OPENROUTER_API_KEY~. *Both are needed*: without both, deploy only
   prints a warning and every bot silently keeps the no-LLM behaviour. ~LLM_CONTEXT_AUTHOR_SALT~ is required anyway (see
   [[*GitHub Deploy Workflow (current target)][the deploy workflow]]).
2. Make sure the bot has its ~<id>_persona.md~ and ~<id>_reply_catalogue.json~ (see ~agent-context/tasks/GeneratePersona.md~).
   A bot whose persona or catalogue is missing or too large for the prompt budget logs the reason at startup and stays
   without the LLM.
3. In a chat, someone runs ~/llm on~ (Telegram, Discord) or ~!llm on~ (IRC). Nothing is sent to a provider from a chat
   that did not do this: the switch is per chat *and* per bot.

| Command | Effect |
|---|---|
| ~/llm on~ / ~/llm off~ | enable / disable the LLM replies of this bot in this chat (disabling also stops remembering messages) |
| ~/llm status~ | tell whether it is on |
| ~/llm forget~ | delete the remembered conversation of this chat, keeping the switch |

The command also has to be offered by BotFather: each bot's ~commands.txt~ already has the ~llm~ line, paste it with
~/setcommands~.

*** When a bot answers

The bot asks the LLM only for a plain message that is /directed at it/ (it is mentioned, one of its messages is replied to,
or on IRC the text starts with ~botname:~), that matched no reactive reply, in a chat with the switch on and outside the
chat timeout (the cooldown that also limits the reactive replies). A matching reactive reply blocked by the timeout does
not fall through to the LLM: a message that matched a reply bundle, also a blocked one, is never asked. The model can answer
with a new text or stay silent; it can also /reuse/ one of the bot's known replies (sent as is), but that needs candidate
replies and today none are offered (see [[file:docs/bot-logic-overview.md][bot-logic-overview]]). Anything malformed, unsafe
(a command, a mention, empty) or failed is dropped without a reply.

The reply language is the one the *persona* states (~xah~ is English only); Italian is only the default for a persona
that states none.

*** Privacy

- *Enabled chats may send their messages to both Gemini (Google) and OpenRouter.* ~LLM_PRIMARY_PROVIDER~ (default
  ~openrouter~) chooses the primary; the other provider is always the fallback and gets the same prompt when the primary fails
  or is out of quota. With the defaults that is OpenRouter first, Google second. The prompt holds the persona, the candidate
  replies, the recent conversation of the chat and the message.
- Senders are never sent: each one is a salted hash (~user-ab12cd34~), mentions and usernames are replaced by a generic
  label. The salt is ~LLM_CONTEXT_AUTHOR_SALT~: keep it secret and stable.
- The conversation is kept in the ~llm_context~ table for ~LLM_CONTEXT_TTL~ (default 7 days) and only while the switch is on;
  ~/llm forget~ deletes it at once.
- *Free tiers:* the Gemini free tier may not be offered to minors or to users in the EEA, UK and Switzerland, and free-tier
  data may be used by the provider. Check the current terms before enabling it in such chats: this is an open question in
  the spec, not something the code enforces.

*** Who can switch it

*The switch is open*: ~/llm on|off|forget~ has no permission check, so any member of a chat can turn it on (and start the
storage of the anonymised messages) or off, or wipe the context. The adapters do not expose the chat-admin status of a
sender today. What bounds the damage: the per-chat and per-bot opt-in, the shared client-side quota (below) which stops the
spending, the anonymisation and the TTL above, and the ops notice when a quota is exhausted. If that is not enough for a
chat, do not add the bot there or ask for an admin-only check (it needs a new field in ~Message~).

*** Configuration

The deploy workflow only injects the three secrets above. Every other value is a default in
~modules/main/src/main/resources/application.conf~, overridable with the environment variable of the OpenRC script or by
editing the file.

| Variable | Default | Meaning |
|---|---|---|
| ~LLM_PRIMARY_PROVIDER~ | ~openrouter~ | the other provider is always the fallback; switching is only this value |
| ~LLM_TIMEOUT~ | ~10 seconds~ | one provider call *and* the whole LLM answer of the engine (see below) |
| ~LLM_MAX_INPUT_TOKENS~ | ~18432~ | prompts above this (4 characters per token) are refused locally, with an ops notice |
| ~LLM_MAX_OUTPUT_TOKENS~ | ~1024~ | output limit sent to the provider |
| ~LLM_CONTEXT_MAX_MESSAGES~ / ~LLM_CONTEXT_MAX_TOKENS~ | ~20~ / ~2048~ | the conversation window of a prompt |
| ~LLM_CONTEXT_TTL~ / ~LLM_CONTEXT_CLEANUP_CRON~ | ~7 days~ / hourly | retention and its cleanup job |
| ~GEMINI_MAX_PER_MINUTE~, ~GEMINI_MAX_PER_DAY~ (same for ~OPENROUTER_~) | ~20~ / ~50~ | client-side quota of each provider, shared by all the bots. The OpenRouter values are the documented free-tier limits; *the Gemini ones are provisional* (#1483 did not measure them), so check them against your key |
| ~OPENROUTER_MODEL~ | empty | empty: ~openrouter/free~ (free router). Set it only to choose a model; one without ~:free~ is paid |
| ~LLM_TRACE_ENABLED~ / ~LLM_TRACE_TTL~ | ~false~ / ~1 day~ | opt-in debug trace of the full prompt and raw response, see [[file:docs/monitoring.md][monitoring]] |

*** Sizing the prompt, the persona and the timeout together

- *Persona size.* The persona gets what the other parts of the prompt leave: ~LLM_MAX_INPUT_TOKENS * 3 - LLM_CONTEXT_MAX_TOKENS * 4
  - 4096 (template) - 8192 (catalogue) - 2048 (message)~ bytes (the 3 is accented Italian, about 3 characters per token). With
  the defaults that is *32 768 bytes*. Startup refuses a persona above it (the bot goes without the LLM) and
  ~sbt checkPersona~ (also in CI) fails on it, together with a hard limit of 64 KiB. Raising ~LLM_MAX_INPUT_TOKENS~ or lowering
  ~LLM_CONTEXT_MAX_TOKENS~ makes room.
- *The limit has to suit the fallback too.* The default input limit is sized for Gemini. The fallback asks OpenRouter
  for ~openrouter/free~ unless ~OPENROUTER_MODEL~ is set (empty by default): OpenRouter then picks a free model per request, so
  its context window and speed are not under our control and may be smaller or slower than ~LLM_TIMEOUT~ allows with a large
  persona. There is one input limit for both providers (a per-provider limit is not implemented), so keep the persona small
  enough for the smallest free model you can tolerate, or set ~OPENROUTER_MODEL~ to a model with at least that window. A model
  without the ~:free~ suffix is *paid*: startup logs a warning for it, because an old ~OPENROUTER_MODEL~ left in a deployment would
  bill every fallback call. The router may also choose a model that lacks a feature the request uses (the request asks for JSON
  output): a refused request shows as ~failure=rejected~, so watch it in the dashboard after a rollout. Free models may also log
  prompts (see the privacy notes above).
- *The timeout is one value used twice.* ~LLM_TIMEOUT~ bounds each provider call and, in the engine, the whole LLM answer. A
  primary that /times out/ therefore leaves no time for the fallback within the same message: the fallback helps for
  fast failures (a 429, a 5xx, a malformed or rejected reply), not for a slow primary. A timeout still spends the quota of
  the provider that was called. Size ~LLM_TIMEOUT~ for the slowest provider you rely on and watch ~failure=timeout~ in the
  dashboard.

** Operations

  Runbook of the production VM. The directory is the repository variable ~DEPLOY_DIR~ (the user is ~DEPLOY_USER~,

*** Path configuration

  Runtime and tests resolve paths from explicit configuration, not from the directory they were launched from:
  - ~sbots.repoRoot~ :: repository root (injected by sbt for tests and forked ~run~; set to ~DEPLOY_DIR~ in production).
  - ~sbots.projectRoot~ :: root of the current sbt project/module; defaults to ~sbots.repoRoot~ when not set.
  - ~sbots.logFile~ :: optional crash-history file. When unset, a crash is only logged and signalled: no ~log.txt~ is
    created in the working directory. The deployed service sets it to ~DEPLOY_DIR/log.txt~.

*** Where the logs are

  - *Grafana Cloud* (first choice, no SSH): [[https://glowingdate3125.grafana.net/explore][Explore]] with the
    ~grafanacloud-glowingdate3125-logs~ data source and the query ~{app="sbots"}~; 14 days of retention. Shipping is on
    only when ~LOKI_URL~, ~LOKI_USER~ (variables) and ~LOKI_TOKEN~ (secret) are set.
  - *On the VM*, in ~DEPLOY_DIR~:
    - ~sbots.log~ :: the standard output of the service (the same lines as the ones in Grafana).
    - ~sbots.err.log~ :: the standard error of the service.
    - ~log.txt~ :: the history of how the application ended (crashes with the stack trace), only grows. Written only
      because the service sets ~sbots.logFile~; it is not created by an unset/default launch.
    - ~oom.hprof~ :: the heap dump of an ~OutOfMemoryError~; it is deleted when the service is started again.
  - *Rotation*: ~logrotate~ (hourly, from ~/etc/periodic/hourly~) rotates ~sbots.log~, ~sbots.err.log~ and ~log.txt~ at
    20 MB, keeps 5 compressed files (~copytruncate~). Installed by the deploy workflow.
  - *Download without SSH*: run the workflow "Download Prod DB and log files" (Actions, ~workflow_dispatch~): the
    artifacts are the DB (~prod sqlite-db~), ~log.txt~ (~prod logTxt~) and ~sbots.log~ with ~sbots.err.log~
    (~prod sbots logs~).

*** Dashboards and alerts

*** Restart and status

  The bots run as the OpenRC service ~sbots~ (~/etc/init.d/sbots~, supervised and respawned after a crash). On the VM:

  #+begin_src shell
  sudo rc-service sbots status
  sudo rc-service sbots restart      # or stop / start
  tail -f DEPLOY_DIR/sbots.log
  #+end_src

  A redeploy of the current ~main~ is the other way to restart: run the workflow "Deploy" (~workflow_dispatch~).

*** Rollback

  - *Code*: the Deploy workflow runs after the CI of every commit on ~main~. Revert the bad commit
    (~git revert <sha>~), merge the revert and the deploy puts the previous behavior back.
  - *Database*: every deploy migrates the production data into a new DB (~DBMigration.sql~, ~scripts/updateProdDB.sh~).
    If the migration fails the production DB is restored by the script and the deploy stops. When it succeeds the
    previous production DB is kept as ~botDB.sqlite3.bak~ (only the last one). To go back to it:

    #+begin_src shell
    sudo rc-service sbots stop
    cd DEPLOY_DIR
    mv botDB.sqlite3 botDB.sqlite3.broken && cp botDB.sqlite3.bak botDB.sqlite3
    sudo rc-service sbots start
    #+end_src

    The data written after that deploy (timeouts, subscriptions, counters) is lost, and an older jar may not
    work with the DB of a newer schema: roll the code back too.
  - To check a migration before deploying it: ~scripts/checkDBMigration.sh~ (from the repository root, after ~sbt dbSetup~).

  - ~DEPLOY_DIR~
  - ~WEBHOOK_PUBLIC_HOST~
  - ~LOKI_URL~ and ~LOKI_USER~ (optional, Grafana Cloud Loki: base url of the stack and user id)

  Required repository secrets:

  - ~SSH_PRIVATE_KEY~ :: private key used by GitHub Actions to connect via SSH
  - ~DEPLOY_SUDO_PASSWORD~ :: password used for ~sudo~ while installing/updating runtime packages
  - bot tokens (eg ~ABAR_TOKEN~, ~CALA_TOKEN~, etc.) as already used by the workflow
  - ~LLM_CONTEXT_AUTHOR_SALT~ :: secret used to hash sender ids in LLM chats. The app *refuses to start* without it,
    and the deploy fails early if it is missing. Generate it once (eg ~openssl rand -hex 32~), set it as a repository
    secret, and keep it stable: changing it rewrites every anonymous sender label in the stored conversations.
  - ~GEMINI_API_KEY~ and ~OPENROUTER_API_KEY~ (optional: without both, LLM replies are disabled)
  - ~LOKI_TOKEN~ (optional, with ~LOKI_URL~ and ~LOKI_USER~: without all three the logs are not shipped)

  Notes:

  - The deploy and webhook endpoints are configured through repository variables, so no host/IP value needs to stay hardcoded in the workflow file.
  - ~webhook-certificate~ (~telegram~ block), ~keystore-path~, and ~keystore-password~ (~http~ block) are optional. If omitted, the app can run behind a reverse proxy that terminates TLS.
  - For better security, prefer adding the server fingerprint to ~known_hosts~ instead of using ~StrictHostKeyChecking=no~.

**** Webhook Extra Configuration

  If something doesn't work, please follow [[https://core.telegram.org/bots/webhooks#the-verbose-version][this guide]] and update the documentation accondingly
  Follow these steps to set up the server property:

  - Server Prerequisites :: Check [[https://core.telegram.org/bots/webhooks#the-short-version][this page]] for the prerequisites required by telegram to work with webhook. In our case, we choose port 8443 for SSL connection.
  - Open Port on OCI Subnet :: The instance where the bots are running needs to have an attached VNICs([[https://docs.oracle.com/iaas/Content/Network/Tasks/managingVNICs.htm][Virtual Network Interface Card]]) with a subnet. The subnet will have a default security list containing the rules for the ports available from outside. Add a new rule for the port required and save it. The parameters to use are:
    - Stateless: No
    - Source: 0.0.0.0
    - IP Protocol: TCP
    - Source Port Range: All
    - Destination Port Range: 8443
    This should allow telegram to reach your server through that port.
  - Test the port is open :: by spawning a server with the command ~python3 -m http.server 8443~ and try to open a browser tab to the server. eg http://129.152.27.196:8443/
  - Generate a keystore JKS :: On the server, using the commands on [[https://core.telegram.org/bots/self-signed][this page]], follow the instruction for the java keystore, pasting each command one by one. For the correct keystore password to use, check the `application.conf`. Example

*** Deploy

 - Set the ~main/src/resources/application.conf~ accordingly. There is a block for the HTTP server (~http~) and one for each platform (~telegram~):
   - ~telegram.webhook-base-url~ as ~https://<serverip>:<outsideport>~, eg ~https://129.152.27.196:8443~
   - ~http.host-url~ as ~0.0.0.0~
   - ~http.port~ as ~<internalPort>~ in our case ~8443~
   - ~telegram.webhook-certificate~ (optional) with the path of the public certificate, eg ~sbotsCertificatePub.pem~
   - ~http.keystore-path~ (optional) add the path to the keystore, eg ~sbotsKeystore.jks~
   - ~http.keystore-password~ (optional) add the password of the keystore, eg ~sbotsKeystorePassword~
   - ~telegram.ops-chat-id~ the Telegram chat that gets the notifications of the operators (errors, bots started), env ~TELEGRAM_OPS_CHAT_ID~
   - If TLS is terminated by a reverse proxy (nginx/caddy/traefik), leave the three options above unset and expose only the internal app port to the proxy.
 - Run ~sbt "clean; main/assembly"~ to create the fat jar
 - Move the fat jar to the VM by ~rsync~ and ~ssh~. Eg. ~rsync -P -e "ssh -i <<private key of the vm>>" <<path to the fat jar -> sBots/main/target/scala-*/main.jar>> <<user of the vm>>@<<public IP of the vm>>:/home/<<user of the vm>>/main.jar~ (~rsync -P -e "ssh -i ubuntu_rsa.pem" /home/benkio/workspace/sBots/main/target/scala-*/main.jar ubuntu@129.152.27.196:/home/ubuntu/bots/main.jar~)
 - Move the ~botDB.sqlite~ if not present in the same way before. If an update to the ~media~ needs to be done, better to dump the current database in order not to lose the ~timeout~, ~subscription~, or other changes in the process. No easy way to migrate the database as of now.
 - Login to the VM
 - OPTIONAL: be sure to have the right environment variables. IT'S RECOMMENDED TO
   CHANGE the ~application.conf~ (point 1) before running the ~assembly~. The environment variables could lose their value somehow.
 - Run the bots.
   - Polling: ~java -Xmx512m -Xms512m -cp main.jar com.benkio.main.MainPolling~ (all the bots) or ~... com.benkio.main.MainPolling rphjb XahLeeBot~ (only the bots named, by id or name; from sbt: ~sbt "main/runMain com.benkio.main.MainPolling rphjb"~)
   - Webhook: ~java -Xmx512m -Xms512m -cp main.jar com.benkio.main.MainWebhook~
 - press ~Ctrl+Z~, run ~bg~ and ~disown~ in order to let previous command run in background
 - close your terminal and enjoy
